# Operating modes

All modes share the same knowledge, workflows and safety layer; they differ in who/what
actuates the engine and the interaction channel.

## 1. Offline
Inputs: tune file(s), log file(s). Output: findings, recommendations, optionally a modified
tune file plus a human-readable diff. No writes to any ECU. Default and safest mode.

## 2. Road tuning
Load is not controllable; the driver is the actuator. The agent plans and sequences runs.

### Run cards
A run card is a short, unambiguous instruction for one test condition:
`id, purpose, gear, target (rpm/load/speed), duration/shape, throttle description, abort conditions, conditions required (warm, road, safe)`.
Examples: "3rd gear, hold 2000 rpm, light steady throttle, 30 s", "3rd gear, full throttle pull from 3000 rpm to redline, then lift".
Run cards are generated by the workflow (which cell/region needs data) and ordered to minimise
risk and time (e.g. steady-state before pulls; low load before high load; knock-safe first).

### Roles
- **Two-person:** operator runs the agent, relays to the driver. Agent addresses the operator.
- **Solo, screen:** run cards read before moving; analysis when stopped.
- **Solo, voice (preferred for solo):** hands-free conversation while driving (below).

### Voice interaction protocol (solo road tuning)
The harness supplies speech-to-text and text-to-speech; this skill defines the *content protocol*.
- **Brevity:** driver-facing utterances <= ~15 words, one instruction at a time, no tables or numbers lists.
- **Priority classes:** SAFETY (immediate, overrides everything) > ABORT > INSTRUCTION > STATUS > CHAT.
- **Fixed phrases:** "run card <n>: ...", "ready?", "go", "hold", "good, lift", "abort", "log mark".
  Driver replies are short and fuzzy-matched ("ready", "go", "abort", "mark", "repeat", "stop").
- **Agent never distracts mid-pull:** during a pull the agent says only abort/safety calls. Results
  are summarised after the run ("clean, no knock, lambda 0.80 at peak") and decisions deferred to a stop or low-risk cruise.
- **Driver may talk:** observations ("heard pinging", "boost spiked") are logged as timestamped notes and correlated with data.
- **No live ECU writes while moving** unless a future live mode explicitly permits bounded changes
  and the safety layer allows it (default: forbidden).
- **Confirmation pattern:** before any change that affects the next run, agent states the change in one sentence and waits for "yes/no".
- **Road safety:** agent insists on suitable conditions (legal, clear, safe road); driving safety outranks data collection.
- **Fallback:** if voice latency/recognition is poor, drop to run-cards-and-stop.

### Data-quality gates (road is noisy)
Warm engine, stable ECT/IAT, valid wideband (post warm-up), gear/speed consistency,
steady-state detection window, wind/gradient notes, battery voltage. Runs failing gates are discarded or down-weighted.

## 3. Dyno
Load, RPM and steady-state are controllable. Enables systematic grid mapping (steady-state
points for VE/fuel/ign), controlled sweeps, repeatability and (with tooling) real-time tuning.
Workflow differences: denser data, tighter steady-state criteria, cell-by-cell closed loop,
temperature/airflow management is the operator's responsibility (agent reminds).

## 4. Live (MCP) overlay
Any of the above can be augmented when an ECU tool exposes the MCP interface
(docs/MCP-INTERFACE.md): live channel reads, table reads, and gated writes. Live capability is
negotiated; absence degrades gracefully to file-based flow.

## Autonomy ladder
`advise` -> `file edit with diff` -> `live propose, human approves` -> `live bounded autonomous`.
Each rung requires the safety conditions in docs/SAFETY.md. Default: advise.
